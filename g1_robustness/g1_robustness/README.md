# Does domain randomization make RL humanoid walking more robust?  (Unitree G1, Isaac Lab, NVIDIA Brev)

Two feed-forward PPO walking controllers are trained with the **same** network, reward, and budget:

| | Baseline | Domain randomization (DR) |
|---|---|---|
| Task ID | `G1-Flat-Baseline-v0` | `G1-Flat-DR-v0` |
| Ground friction | fixed: static 0.8 / dynamic 0.6 | random per robot: static 0.4–1.2, dynamic 0.3–0.9 |
| External pushes | none | velocity kick, ±0.6 m/s per axis (x, y), every 6–10 s |
| Everything else | identical (G1 flat task, forward command 0–0.8 m/s, 20 s episodes, stock PPO, 1500 iterations) | |

Stock Isaac Lab G1 mass randomization is removed from **both** so that friction and pushes are the only difference.
They are then tested on identical conditions, including friction values and push strengths never seen in training.

> **Status:** the plotting script was tested on synthetic data. The Isaac Lab scripts (`g1_dr/`, `evaluate.py`, `record_demo.py`) were
> written against the Isaac Lab 2.x API but could not be run in the environment where this was prepared (no Isaac Sim there).
> Do Step 3 (smoke test) before committing GPU hours, and see Troubleshooting if a name or signature differs in your version.

There is no dataset to download: all data is generated by simulation.

## Step 1: Create the Brev instance
1. Sign in at https://brev.nvidia.com. Easiest route: open the **Isaac Lab launchable** (search "Isaac Launchable" / "Isaac Lab" in Brev's Launchables) and click **Deploy Launchable**.
2. Choose a GPU with **RT cores** so videos can render: **L40S** (48 GB) is a good default; RTX 6000 Ada or A10G also work.
   A100/H100 can train headless but cannot render the Isaac Sim scene, so you could not record videos on them.
3. Wait until the instance shows running and the setup script has finished (the first launch can take a long time). Open VS Code / the terminal from the instance page.
4. **Billing runs while the instance is on, even idle.** Stop it when you take breaks, delete it when done (Step 9).
5. Check the machine:
   ```bash
   nvidia-smi
   ls ~ /workspace 2>/dev/null          # find the IsaacLab folder
   export ISAACLAB=/path/to/IsaacLab    # only needed if the scripts cannot find it
   grep -m1 '^version' $ISAACLAB/source/isaaclab/config/extension.toml
   ```
6. **Version check (important).** This project targets **Isaac Lab 2.x** (task `Isaac-Velocity-Flat-G1-v0`, script `scripts/reinforcement_learning/rsl_rl/train.py`). Isaac Lab 3.0 has a different CLI and config layout (see Troubleshooting).
   If your instance has 3.x, check out the 2.3 release in a second folder instead (needs Isaac Sim 5.1):
   ```bash
   git clone -b release/2.3.0 https://github.com/isaac-sim/IsaacLab.git ~/IsaacLab23
   # follow its installation guide (pip install isaacsim==5.1.* then ./isaaclab.sh --install), then: export ISAACLAB=~/IsaacLab23
   ```

## Step 2: Put the project on the instance and run setup
Upload `g1_robustness.zip` through the VS Code file explorer (drag and drop), or `git push` it to a repo and clone it.
```bash
cd ~ && unzip g1_robustness.zip && cd g1_robustness
bash scripts/00_setup.sh
```
Expected: the version line, your GPU, and `G1-Flat-Baseline-v0` and `G1-Flat-DR-v0` listed among the tasks.

## Step 3: Smoke test (about 5–10 min)
```bash
bash scripts/01_smoke_test.sh
```
It trains each task for 30 iterations. Note the "steps/s" or per-iteration time, then estimate the full run:
`total time = 1500 × seconds per iteration`. Multiply by 6 runs (2 groups × 3 seeds) to budget your hours.
Delete the throw-away logs: `rm -rf $ISAACLAB/logs/rsl_rl/*/*_smoke`.

## Step 4: Train (the long step)
Run inside `tmux` so a dropped connection does not kill it:
```bash
tmux new -s train
bash scripts/02_train_all.sh            # SEEDS="1 2 3" NUM_ENVS=4096 ITERS=1500 by default
# detach: Ctrl-b then d      re-attach: tmux attach -t train
```
- Runs alternate baseline / DR per seed, so if you run out of time you still have a matched pair.
- Out of GPU memory: `NUM_ENVS=2048 bash scripts/02_train_all.sh` (keep it identical for both groups).
- If the budget is tight, use `SEEDS="1 2"`; with fewer than 3 seeds, state clearly that variance estimates are weak.
- Watch progress: `$ISAACLAB/isaaclab.sh -p -m tensorboard.main --logdir $ISAACLAB/logs/rsl_rl --port 6006`, then expose port 6006 via Brev's port/secure-link settings.
- Checkpoints: `$ISAACLAB/logs/rsl_rl/g1_flat_{baseline,dr}/<timestamp>_{baseline,dr}_s<seed>/model_1499.pt`.

Quick qualitative check of a trained policy (optional, needs a display/stream; skip on headless):
```bash
cd $ISAACLAB && ./isaaclab.sh -p scripts/reinforcement_learning/rsl_rl/play.py --task G1-Flat-DR-v0 --num_envs 16 --headless --video --video_length 300
```

## Step 5: Evaluate on identical test conditions
```bash
bash scripts/03_eval_all.sh
```
- Grid: friction μ ∈ {0.1, 0.2, 0.3, 0.5, 0.8, 1.0, 1.2, 1.5} × push ∈ {0, 0.25, 0.5, 0.75, 1.0, 1.25, 1.5} m/s, pushes every 4 s.
- Every policy sees the same robots/seed, the same command (walk straight at 0.6 m/s), 100 episodes per cell, one 20 s episode per robot.
- **Held-out** = friction outside [0.4, 1.2] or push above 0.6 m/s (also a different push interval than training).
- Output: `results/eval_mu<μ>.csv` (one per friction value). To redo, delete the CSVs.

Metric definitions:
| Metric | Definition |
|---|---|
| fall | episode terminated before 20 s (G1 task: torso contact with the ground) |
| survival rate | fraction of episodes without a fall |
| **success rate** | no fall **and** mean horizontal velocity error < 0.25 m/s (`--success_err`) |
| falls / min | falls ÷ total simulated minutes of walking |
| velocity-tracking error | mean ‖v_xy − cmd_xy‖ (m/s) over the episode; yaw-rate error also saved |

## Step 8: Write the report
Fill in `report_template.md` with your numbers and figures. Be honest about:
- Fig. 1 rewards are measured under each group's own training conditions, so they are not directly comparable.
- Seed count (3 seeds gives only a rough std; do not claim statistical significance from it).
- Findings may go either way: DR can cost a little nominal performance, and may not help for out-of-range conditions. Report what you see.

Download `results/`, `figures/`, `videos/`, the `logs/rsl_rl` checkpoints (small), and `g1_dr/` via the VS Code explorer (right-click → Download) or `brev` CLI copy. Then **stop or delete the instance** on the Brev page.

## Design choices and limits
- Friction is sampled once per robot at startup (Isaac Lab's standard approach), so 4096 robots cover the range. Evaluation uses fixed friction with dynamic = 0.75 × static.
- Both groups use the stock G1 observation noise, reward, and terminations. Evaluation keeps the training observation noise (`--no_obs_noise` turns it off).
- Not included (as in the proposal): hardware, sim-to-real, stairs, jumping, manipulation.
- Optional extension: add a friction-only and a push-only task (copy `G1FlatDREnvCfg`, drop one term) to see which factor matters.

## Troubleshooting
| Symptom | Fix |
|---|---|
| `G1-Flat-*` tasks not listed | Check the symlink `$ISAACLAB/source/isaaclab_tasks/isaaclab_tasks/manager_based/locomotion/velocity/config/g1_dr`; look for an import error with `./isaaclab.sh -p -c "import isaaclab_tasks"` after launching, or run train.py and read the traceback. |
| `ImportError ... G1FlatEnvCfg / G1FlatPPORunnerCfg` | Class names differ in your version: open `.../config/g1/flat_env_cfg.py` and `.../g1/agents/rsl_rl_ppo_cfg.py` and adjust the imports in `env_cfgs.py` / `agent_cfgs.py`. |
| `AttributeError` on `cfg.events.physics_material` or `commands.base_velocity` | Same: field names differ, inspect `velocity_env_cfg.py` in your version. |
| Isaac Lab 3.0 (`isaaclab train ...`, `default_agent`) | Use the 2.3 release (Step 1.6), or port: task IDs lose the `-v0`, the agent entry-point key and the root-velocity/event APIs changed (see the "Migrating to 3.0" doc). |
| Friction warning "dynamic > static" | Narrow `DR_DYNAMIC_FRICTION` in `env_cfgs.py` (and evaluation uses 0.75×static, which is always valid). |
| `KeyError: time_outs` | Already handled by a fallback; if it persists, use `u.termination_manager.time_outs`. |
| CUDA out of memory | Lower `NUM_ENVS` (training) or `ENVS_PER_LEVEL` (evaluation). |
| Video recording fails / black frames | Needs an RTX-class GPU and `--enable_cameras` (set automatically); do not use A100/H100. |
| `runner.load` shape mismatch | Evaluate with the same task family the checkpoint was trained with (both share the same network, so this means the config was edited after training). |
